# Golden Pipeline Enterprise Integration Requirements

## Purpose and scope

This document describes the Golden Pipeline's current Artifactory integration, its supporting dependencies, and future ServiceNow and Rally integration opportunities. ServiceNow and Rally implementation is future work; this story captures the integration opportunities and known dependencies.

## Artifactory

**Status:** Integrated for current build-image use; runner and authentication are configured.

Artifactory currently serves as a registry for images used during the build process. These build images are separate from the application image used for deployment. The current integration scope therefore covers build-image consumption, without claiming that the deployed application image comes from Artifactory.

The integration depends on:

- A GitHub Actions runner with network access to Artifactory.
- Configured authentication for the required registry operations.
- The workflow or script that retrieves and uses the build image.

Record the following implementation references alongside this document:

| Detail | Current information |
| --- | --- |
| Runner | Configured; add runner label or runner-group reference. |
| Authentication | Configured; add the credential reference and how it is passed to the workflow. Do not include credential values. |
| Image retrieval | Build images are consumed from Artifactory; add the image/repository reference. |
| Publication | Record any image or artifact publication separately, if applicable. |
| Workflow or script | Add the responsible reusable workflow or script path. |
| Execution evidence | Add a successful run showing retrieval and use of the build image. |

Application artifact publication, downstream retrieval, and deployment consumption should be recorded separately if those flows are included in the implementation. Build-image use alone does not establish those flows.

## ServiceNow / CMDB

**Status:** Future integration; opportunities documented below.

- **CMDB records and lifecycle:** Associate GitHub repositories/projects with application or project records, ownership, criticality, access, decommissioning, and archiving.
- **Project creation workflows:** Connect repository/project creation with ServiceNow forms or workflows and the associated CMDB information.
- **Deployment/change approval:** Evaluate connecting ServiceNow change authorization to GitHub deployment gates so deployment waits for the appropriate approval. GitHub custom deployment protection rules / GitHub Apps are a potential approach to evaluate.
- **Deployment traceability:** Associate commits, builds, tests, artifacts, approvals, and deployment information with the relevant ServiceNow change record.

Connectivity, authentication, and the final integration approach remain TBD.

## Rally

**Status:** Future integration; opportunities documented below.

- **Defect integration:** Allow pipeline quality or security findings to create, update, or associate Rally defects where appropriate. Relevant context could include repository, environment, failed check, severity, and related work item.
- **Work-item traceability:** Carry Rally feature, story, or defect references through commits, pull requests, builds, releases, and deployments so delivery activity can be traced to the originating work.
- **Verify integration boundary:** Keep Verify quality-check work separate from Rally defect automation until the interface between them is defined. This document does not establish that defect automation is implemented.

Connectivity, authentication, and the final integration approach remain TBD.
